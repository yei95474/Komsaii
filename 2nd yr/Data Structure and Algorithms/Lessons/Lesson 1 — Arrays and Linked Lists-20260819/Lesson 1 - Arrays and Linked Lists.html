Abstract Data Types and Arrays

What data structures are, how arrays work in memory, and how to analyze their operations

First section: Abstract Data Types and Arrays. We'll start with what a data structure actually is, then the idea of an ADT, then how arrays sit in memory and the four core operations — access, search, insert, and delete — and wrap up with a complexity summary for arrays.

What Is a Data Structure?

Data Structure — An organized arrangement of data in memory that enables efficient storage, retrieval, and modification. The choice of structure determines the performance of every operation performed on that data.
  • Data structures store values and define the relationships between them
  • Each structure supports a fixed set of operations (e.g., insert, search, delete)
  • No single structure is best for every problem — choosing well is a core engineering skill
  • This course covers linear structures (arrays, lists, stacks, queues) and hierarchical structures (trees)
Lesson 1 — Arrays and Linked Lists
Let me start with a question — when you store your contacts on your phone, what does the software actually have to do? It has to insert new contacts, search for one, delete others. A data structure is just how we organize that data so those operations stay fast. Up here are the six structures we'll meet this semester — arrays, linked lists, stacks, queues, hash tables, and binary search trees. The big idea I want you to leave with: there's no single best structure for everything. Picking the right one is a real engineering decision, not just an implementation detail.

Abstract Data Type

Abstract Data Type (ADT) — A mathematical model that specifies a data type by its behavior (the set of operations and their semantics) without prescribing how that behavior is implemented in memory.

ADT specifies what

  • Supported operations
  • Preconditions and postconditions
  • Observable behavior from the caller's perspective

Implementation specifies how

  • Memory layout (array, nodes, hash table …)
  • Pointer / index management
  • Time and space trade-offs
ℹ The List ADT can be implemented with either an array or a linked list — same interface, different performance characteristics.

Here's a distinction that trips a lot of people up. Think of a TV remote — the buttons are the interface, what you can do. The circuit board inside is the implementation, how it actually works. Two brands can have identical buttons but completely different electronics. That's exactly an ADT versus its implementation: the ADT says what operations exist, the implementation decides how. So if I hand you a List with insert and search, does it matter to you whether it's an array or a linked list underneath? For correctness, no — only the performance changes.

The Array

An array is a finite, ordered sequence of elements of the same type, stored in contiguous memory locations and accessed via a zero-based integer index.

  • Fixed size — declared at creation; cannot grow or shrink (static array)
  • Random access — any element reached in O(1) by index arithmetic
  • Cache-friendly — sequential elements sit in adjacent memory; prefetching works well
Index formula: address(i) = base + i × sizeof(T)
where base is the address of element 0 and T is the element type.

Lesson 1 — Arrays and Linked Lists
An array is just a row of same-type elements sitting in contiguous memory, reached by a zero-based index. Look at the address formula with me. Say our base address is 1000 and each int is 4 bytes — where's index 3? 1000 plus 3 times 4, so 1012. That's it. One multiply, one add, and the CPU has the address. That's why array access is O(1): it doesn't matter if the array holds five elements or five million, the math is exactly the same.

Static vs. Dynamic Arrays

Static Array — int arr[N]

  • Size fixed at compile time
  • Allocated on the stack
  • No overhead — fastest possible allocation
  • Overflow if N is underestimated
  • Waste if N is overestimated

int scores[30];       // fixed: exactly 30 ints
scores[0] = 95;       // O(1) access

Dynamic Array — std::vector<T>

  • Size adjustable at run time
  • Allocated on the heap
  • Amortized O(1) push_back via doubling
  • Slightly higher overhead (capacity, size, pointer)
  • Preferred in production C++ code

std::vector<int> v;
v.push_back(95);      // appends; resizes if needed
v[0] = 88;            // O(1) access
Lesson 1 — Arrays and Linked Lists
Two flavors of array. A static array — int arr[N] — has its size fixed at compile time and lives on the stack: fast, but if you guess N wrong you either overflow or waste space. A dynamic array — std::vector — grows at run time on the heap. Here's the key thing I want you to hold onto: a vector is still a contiguous array underneath. When it runs out of room, it allocates a new block double the size and copies everything over. That copy is O(n), but it happens so rarely that the average cost per push_back is still O(1). And why double instead of adding one slot each time? Because doubling keeps the total number of copies low across many insertions.

Array Operation: Linear Search


// Returns index of target, or -1 if not found
int linearSearch(int arr[], int n, int target) {
    for (int i = 0; i < n; i++) {   // iterate every element
        if (arr[i] == target)
            return i;                // found — stop early
    }
    return -1;                       // not found
}
// Usage: int pos = linearSearch(arr, 5, 42);

Sequentially examines each element until a match is found or the array is exhausted

Linear search: we walk the array element by element until we find the target or run out. Notice the early return the moment we match. Best case, the target's at index 0 — one comparison, done. Worst case, it's at the very end or not there at all, and we check all n elements. For analysis, that worst case is what we care about. So when would you use this over binary search? Only when the array isn't sorted — binary search needs sorted data, but then it gives you O(log n) instead.

Array Operation: Insert at Index


// Insert val at position pos; arr has capacity for n+1 elements
void insertAt(int arr[], int& n, int pos, int val) {
    // Shift elements right to open a slot
    for (int i = n; i > pos; i--)
        arr[i] = arr[i - 1];   // shift right: O(n) in worst case
    arr[pos] = val;             // place the new value
    n++;                        // update size
}
// Insert at tail (no shifting needed)
// arr[n++] = val;   — O(1)

To insert in the middle of an array, you first have to make room. Watch the shifting loop — every element from that position onward slides one slot to the right before we drop the new value in. That shifting is exactly why this is O(n). Picture [10, 25, 42, 3] and inserting 7 at index 1: 25, 42, and 3 all shift right first. The one exception is inserting at the tail — no shifting, so that's O(1). And what if the array's already full? For a fixed-size array, undefined behavior; a vector would just reallocate.

Array Operation: Delete at Index


// Delete element at position pos
void deleteAt(int arr[], int& n, int pos) {
    // Shift elements left to close the gap
    for (int i = pos; i < n - 1; i++)
        arr[i] = arr[i + 1];   // shift left: O(n) in worst case
    n--;                        // update size
}
// Delete from tail: n--;   — O(1)

Deletion is the mirror image. To remove from the middle, everything after the gap shifts one slot left to close it — again O(n). Take [10, 7, 25, 42, 3] and delete index 1, the value 7: then 25, 42, 3 all shift left. One subtle point — the old value is still physically in memory; we just decrement n so it's logically gone. That's fine for an int, but it matters for objects with destructors. Deleting from the tail, of course, is O(1) — just decrement.

Big-O Notation

Big-O — O(g(n)) — An upper bound on the growth rate of a function. We say f(n) = O(g(n)) if there exist positive constants c and n₀ such that f(n) ≤ c · g(n) for all n ≥ n₀.

In algorithm analysis, O(g(n)) describes the worst-case growth rate of an algorithm's resource use (time or space) as input size n grows toward infinity.

  • Drop constants: O(3n) = O(n), O(500) = O(1)
  • Drop lower-order terms: O(n² + n) = O(n²), O(n log n + n) = O(n log n)
  • Focus on the dominant term — the one that grows fastest as n → ∞
ℹ Big-O is the most commonly used notation in practice because it tells us the guaranteed worst-case limit — the most critical bound for system design.
Lesson 1 — Arrays and Linked Lists
Big-O is an upper bound on growth. The formal line says there exist constants c and n-zero so that f(n) stays at or below c times g(n) once n passes that threshold. In plain words: past some point, f never grows faster than g — and we only care about large n, not the small inputs. Two rules fall out of that. Drop constants: O(3n) is still just O(n), proportional to n. Drop lower-order terms: in n² plus n, at n equals a thousand the n² is a million and the n is only a thousand — about a tenth of a percent, so it vanishes. Always keep the dominant term, the one that grows fastest.

Big-Ω and Big-Θ Notation

Big-Ω — Ω(g(n)) — A lower bound. f(n) = Ω(g(n)) means the function grows at least as fast as g(n). Describes the best-case floor on resource use.

Example: Linear search is Ω(1) — in the best case, the target is at index 0 and only one comparison is needed.

Big-Θ — Θ(g(n)) — A tight bound. f(n) = Θ(g(n)) means the function grows exactly as fast as g(n) (both upper and lower bounds match).

Example: Linear search is Θ(n) — average and worst case both grow linearly. It is also O(n) and Ω(1).

Think of an elevator. Big-O is "at most this many floors up" — the upper bound. Big-Omega is "at least this many" — the lower bound, your best case. Big-Theta is "exactly this floor" — when the upper and lower bounds match. Linear search is Omega of 1 in the best case, and Theta of n when average and worst both grow linearly. In day-to-day engineering we mostly use Big-O for worst-case guarantees, Theta when the bound is tight — merge sort is Theta of n log n every single time — and Omega mostly shows up in theoretical lower-bound proofs.

Best, Average, and Worst Case

The same algorithm can behave very differently depending on the input. We distinguish three analysis scenarios:

Best Case

The most favorable possible input — provides a lower bound (Ω) on performance.

Linear search: target at index 0 → 1 comparison

Average Case

Expected performance over all possible inputs — requires probability analysis.

Linear search: target at random position → ~n/2 comparisons

Worst Case

The most unfavorable possible input — provides an upper bound (O) and is the standard for algorithm design guarantees.

Linear search: target absent or at last index → n comparisons

ℹ Unless stated otherwise, Big-O in this course refers to the worst-case scenario.
Lesson 1 — Arrays and Linked Lists
The same algorithm can behave very differently depending on the input, so we name three scenarios. Best case is the lucky input — linear search finding the target at index 0, one comparison. Average case is the expected behavior over all inputs — roughly n-over-2 comparisons. Worst case is the nightmare input — target absent, all n comparisons. We design for the worst case, because that's the one we have to survive. Why not just the average? Because the worst case really does happen in practice — like always feeding a sorted array to a naive quicksort. So unless I say otherwise, Big-O in this course means worst case.

Introduction to Recursion

Recursion — A technique where a function solves a problem by calling itself on a smaller subproblem, until a base case is reached that can be solved directly without further recursion.
  • Base case — the termination condition; prevents infinite recursion
  • Recursive case — breaks the problem into a smaller version of itself
  • Each call is pushed onto the call stack; resolved in LIFO order
  • Every recursive algorithm can be rewritten iteratively (and vice versa)

// Recursive factorial
int factorial(int n) {
    if (n == 0) return 1;    // base case
    return n * factorial(n - 1);
    // recursive case
}

// factorial(3) → 3 * factorial(2)
//              → 3 * 2 * factorial(1)
//              → 3 * 2 * 1 * factorial(0)
//              → 3 * 2 * 1 * 1 = 6

factorial(3) pushes 4 stack frames before unwinding

Lesson 1 — Arrays and Linked Lists
Recursion is when a function solves a problem by calling itself on a smaller piece, until it hits a base case it can answer directly. Look at factorial. The base case is n equals 0 returns 1 — and what happens if I delete that line? Infinite recursion, stack overflow. The recursive case is n times factorial of n minus 1. Trace factorial of 3: it stacks up 3, then 2, then 1, then 0 — four frames — and then unwinds back down, multiplying as it returns: 1, 1, 2, 6. Hold onto this idea, because merge sort and quicksort next lesson are naturally recursive.

Recursion vs. Iteration

Recursive Factorial


int factorial(int n) {
    if (n == 0) return 1;
    return n * factorial(n - 1);
}
  • Elegant and close to the mathematical definition
  • O(n) stack space — one frame per call
  • Stack overflow risk for large n

Iterative Factorial


int factorial(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++)
        result *= i;
    return result;
}
  • Slightly more verbose but no stack overhead
  • O(1) space — single accumulator variable
  • Preferred when recursion depth is large
✓ Both versions are O(n) time. Choose recursion when it makes the algorithm significantly clearer (e.g., tree traversal, divide-and-conquer sorting). Choose iteration when stack depth is a concern.
Lesson 1 — Arrays and Linked Lists

What Is a Linked List?

Linked List — A linear data structure in which elements (called nodes) are stored at non-contiguous memory locations. Each node holds a data value and one or more pointers to adjacent nodes, forming a chain.

Unlike arrays, linked lists do not require contiguous memory — nodes may be scattered anywhere on the heap.

  • No fixed capacity — grows and shrinks dynamically
  • Insertion and deletion at the head are O(1) — no shifting
  • No index-based random access — must traverse from the head
  • Each node carries a pointer overhead (4–8 bytes per node)

Insert at head — three steps, and the order is everything. Step one, allocate the new node. Step two — and this is the critical one — point the new node's next at the current head, before you touch head. Step three, move head to the new node. Now why must step two come first? Because the instant you do head equals newNode, head stops pointing at the old first node — and if you hadn't saved that link yet, the entire rest of the list is gone. Three pointer operations, no traversal, so this is O(1) no matter how long the list is.

Singly Linked List: Insert at Tail

void insertTail(Node*& head, int val) {
    Node* newNode = new Node{val, nullptr};
    if (head == nullptr) {              // empty list edge case
        head = newNode; return;
    }
    Node* curr = head;
    while (curr->next != nullptr)       // traverse to the last node
        curr = curr->next;
    curr->next = newNode;               // link last node to new node
}
// Time: O(n) — must traverse entire list to reach the tail

Singly Linked List: Delete a Node

void deleteByValue(Node*& head, int val) {
    if (head == nullptr) return;         // empty list
    if (head->data == val) {             // delete head node
        Node* temp = head;
        head = head->next;
        delete temp; return;
    }
    Node* prev = head;
    while (prev->next != nullptr && prev->next->data != val)
        prev = prev->next;              // find node before target
    if (prev->next == nullptr) return;  // value not found
    Node* target = prev->next;
    prev->next = target->next;          // bypass the target node
    delete target;                      // free memory
}
// Time: O(n) search + O(1) re-link = O(n) overall

Deletion has the most moving parts. First, the edge cases: empty list, and deleting the head itself. For the head, save it in a temp, advance head, then delete temp — never delete before you've advanced, or you lose the list. Otherwise, we find the predecessor — the node whose next points at our target. Then we re-link: prev-arrow-next jumps over the target to target-arrow-next, and we delete the target to free its memory. On the board: A to B to C, deleting B means A points to C, then delete B. The search is what makes it O(n); the actual re-link is O(1).

Singly Linked List: Traversal


// Print all values in the list
void traverse(Node* head) {
    Node* curr = head;              // start at the head
    while (curr != nullptr) {
        std::cout << curr->data << " ";
        curr = curr->next;          // advance to next node
    }
}
// Search for a value; returns pointer or nullptr
Node* search(Node* head, int val) {
    for (Node* curr = head; curr != nullptr; curr = curr->next)
        if (curr->data == val)
            return curr;
    return nullptr;
}

Doubly Linked List

Doubly Linked List (DLL) — A linked list in which each node holds pointers to both the next and previous nodes, enabling traversal in both directions. 

struct DNode {
    int data;
    DNode* next;     // pointer to next node
    DNode* prev;     // pointer to previous node
};
// null ← [10] ⇄ [25] ⇄ [7] → null

// Delete a node (no predecessor search needed)
void deleteNode(DNode*& head, DNode* target) {
    if (target->prev) target->prev->next = target->next;
    else head = target->next;          // target was head
    if (target->next) target->next->prev = target->prev;
    delete target;
}

A doubly linked list adds a second pointer — prev — so each node knows both its neighbors. Watch what that buys us on delete: because we can reach the predecessor directly through prev, deleting a known node is O(1) — no traversal at all. That's the big win over a singly linked list. The cost is an extra pointer per node, so more memory. By the way, std::list in the C++ standard library is exactly this. Real-world fits? Browser history, undo-redo in an editor, previous-and-next track in a music player.

Circular Linked List

Circular Linked List — A linked list in which the tail node's next pointer points back to the head (instead of nullptr), forming a closed loop with no natural end.
  • Traversal must use a stop condition other than nullptr
  • Can be singly or doubly linked
  • Every node has equal access to all others — no privileged "start"
⚠ A naive traversal loop without a stop condition will run infinitely on a circular list.

In a circular list, the last node's next loops back to the head instead of pointing to null — so there's no natural end. Think of a round-robin scheduler: each process gets a time slice, then the next one in the circle, and after the last one we're back at the first. A circular list models that perfectly. But notice the danger — if you traverse it the usual way, checking for null, you'll loop forever, because there is no null. So your stop condition has to be "have I arrived back at head?" — a do-while, or a check after the first step. It can also be doubly circular. Used for round-robin scheduling, circular buffers, turn rotation in games.

Pointer Management Pitfalls

✕ Dangling Pointer — Accessing a node after it has been deleted. 

Node* p = head;
delete p;
p->data;  // undefined behavior!

Fix: Set p = nullptr immediately after delete p.

✕ Memory Leak — Losing all pointers to a node without deleting it. 

head = head->next; // old head is now orphaned
// its memory is never freed!

Fix: Store old head in temp, advance, then delete temp.

✕ Null Dereference — Dereferencing a nullptr pointer. 

Node* curr = head;
while (curr->next != nullptr)  // crashes if head == nullptr!
    curr = curr->next;

Fix: Always check if (head == nullptr) before dereferencing.

⚠ Wrong Order of Pointer Updates — Overwriting a pointer before saving the value it holds causes permanent data loss.

Always save existing pointer values before overwriting them.

Lesson 1 — Arrays and Linked Lists
These four bugs cause most of the linked-list pain you're about to experience. A dangling pointer — using a node after you deleted it — crashes you; the fix is to set the pointer to nullptr right after delete. A memory leak — dropping your only pointer to a node without freeing it — is silent; the program keeps running but bleeds heap memory. A null dereference — touching next when the pointer is null — crashes; so always check for null first. And wrong update order silently loses data. The thread through all of them: C++ has no garbage collector. Every new needs a delete, and every pointer gets checked before you use it.

Linked Lists

  • ✓ Linked lists store nodes at non-contiguous memory addresses linked by pointers
  • ✓ Each node holds a data field and a next pointer (plus prev for DLL)
  • ✓ Insert/delete at head is O(1) — no shifting required
  • ✓ Search and tail insertion (without tail pointer) are O(n) — requires traversal
  • ✓ DLL enables O(1) deletion of a known node and bidirectional traversal
  • ✓ Circular linked list has no null tail — traversal must check for cycle completion
  • ✓ Always check for nullptr, pair every new with delete, and save pointers before overwriting

Cache Behavior

✓ Arrays — Contiguous memory → excellent spatial locality. Adjacent elements are loaded together into the CPU cache. Sequential access is very fast in practice.
⚠ Linked Lists — Nodes scattered in heap memory → poor spatial locality. Each node dereference may cause a cache miss, fetching from main RAM. Practical performance is often much slower than O-notation suggests.
Lesson 1 — Arrays and Linked Lists
Now the difference that Big-O hides. Both are O(n) in space, but the constant factor differs — a linked-list int node spends two-thirds of its bytes just on the pointer. The bigger story is cache. Arrays are contiguous, so neighbors load into cache together and sequential access flies. Linked-list nodes are scattered, so each hop can be a cache miss — and a cache miss is expensive: L1 cache is around four cycles, main RAM around two hundred. So two operations in the same O(n) class can differ by five to ten times in real life. That's the real reason arrays and vectors usually win in performance-critical code.

Use-Case Decision Guide

Choose an Array when…

  • You frequently access elements by index
  • The collection size is known or bounded at creation time
  • You need cache-efficient sequential processing
  • You perform sorting (contiguous memory aids sort algorithms)
  • Memory overhead matters (no pointer cost per element)

Choose a Linked List when…

  • You frequently insert or delete at the head
  • The collection size is unpredictable or frequently changes
  • You implement a stack, queue, or deque (upcoming modules)
  • You need O(1) splicing — inserting a segment into the middle
  • Index-based access is rare or unnecessary
Lesson 1 — Arrays and Linked Lists
So how do you actually choose? Reach for an array — really, std::vector — when you access by index, when the size is known or bounded, and when you want cache-efficient sequential work. In practice, vector is the default choice in C++. Reach for a linked list when you're constantly inserting or deleting at the head, when the size swings unpredictably, or when you're building a stack or queue. One to think about: a text editor inserting characters anywhere — array or linked list? Honestly, neither; specialized structures like gap buffers or ropes win there. But it shows why plain arrays aren't always the answer.
